# Technical Specification: Lupo Spec Native Framework & Evolution Engine

## 1. System Overview

Lupo Spec is a standalone, native Python framework designed for **Spec-Driven Development (SDD)**. It originated as a CLI wrapper around several external Node.js/uv tools but has evolved into a pure, native Python application that implements the core logics of those tools directly by transpiling and porting specific, isolated blocks of code from the original upstream repositories.

It securely routes user intent and architectural generation through natively implemented logic derived from four distinct upstream frameworks:
1. **GitHub Spec Kit (`github/spec-kit`):** For heavy, Day-1 architectural blueprints (Constitution, PRD, Implementation Plan).
2. **OpenSpec (`fission-ai/openspec`):** For lightweight, day-to-day feature deltas (Delta Specs, Change Archiving).
3. **Superpowers (`obra/superpowers`):** For test-driven, agentic execution (Git Worktrees, Red-Green-Refactor loop).
4. **Andrej Karpathy Skills (`forrestchang/andrej-karpathy-skills`):** For behavioral guidelines to reduce common LLM coding mistakes.

Lupo Spec utilizes a strict **Traceability Protocol** to map its native Python logic back to the upstream sources, and an **Evolution Engine** (`sync_repos.py`) to keep itself up to date when the upstream frameworks change.

## 2. Global Directory Structure

The project establishes and conforms to the following directory structure:

```text
/project_root
  ├── sync_repos.py                     # Upgraded Evolution Engine script
  ├── evolution_map.json                # Auto-generated by sync_repos.py
  ├── /spec-kit                         # Cloned repo (GitHub Spec Kit)
  ├── /openspec                         # Cloned repo (OpenSpec)
  ├── /superpowers                      # Cloned repo (Superpowers)
  ├── /andrej-karpathy-skills           # Cloned repo (Behavioral Guidelines)
  ├── /docs                             # Project documentation (Architecture, PRD, etc.)
  └── /src                              # Lupo Spec Native Source Code
      ├── lupospec_cli.py               # Typer/Click command router (`lupo`)
      ├── core/
      │   ├── lupospec_init.py          # Native Python port of Spec Kit's PRD/Arch generation
      │   ├── lupospec_workflow.py      # Native Python port of OpenSpec's propose/archive logic
      │   └── lupospec_agent_execution.py # Native Python port of Superpowers' Git/TDD execution
      └── prompts/
          └── lupospec_BEHAVIOUR.md     # CLAUDE.md auto-copied from the cloned repo
```

## 3. The Traceability Protocol (Critical Requirement)

To prevent Lupo Spec from losing cohesion and to remain maintainable, the code avoids copying entire files from upstream frameworks. It extracts *only* the specific functions or classes required. 

Every single extracted and ported block inside the `/src/core/` files must be wrapped in the following exact comment structure. This ensures the system can track exactly where its logic originated:

```python
# ===================================================================
# LUPO SPEC TRACEABILITY
# Source Repository: [Repo Name] (e.g., fission-ai/openspec)
# Source File: [Relative path in repo] (e.g., src/commands/propose.ts)
# Original Lines: [Start Line] - [End Line]
# Purpose: [Brief description of what this block does]
# ===================================================================

[TRANSPILED/PORTED PYTHON CODE BLOCK GOES HERE]

# ===================================================================
# END LUPO SPEC TRACEABILITY
# ===================================================================
```

## 4. Lupo Spec Architecture & Execution (`/src`)

### Tech Stack
* **Language:** Python 3.11+
* **CLI Framework:** `Typer` or `Click` for terminal interfaces.
* **Process Management:** Python `subprocess` module to stream terminal output.
* **Execution Agent:** Targets **Void Editor** (AI-native code editor, fork of VS Code) via the `void` CLI binary.

### CLI Command Mapping & Core Logic

**Command 1: `lupo init <project_name>`** (Mapped from Spec Kit)
* Creates a greenfield project directory structure.
* Programmatically writes a default `constitution.md`, a PRD template (`spec.md`), and an implementation plan template (`plan.md`) into `/docs/architecture/`.
* Initializes the Git repository natively.

**Command 2: `lupo propose <feature_description>`** (Mapped from OpenSpec)
* Reads existing blueprints from `/docs/architecture/`.
* Generates a new Delta Spec (Change Proposal) in the `openspec/changes/<change-id>/` directory containing the feature description, requirement placeholders, and a task checklist.

**Command 3: `lupo execute [--strategy <auto-heal|tdd>]`** (Mapped from Superpowers & OpenCode)
* Locates the active Delta Spec.
* Loads the dynamic behavioral instructions via `prompts/lupospec_BEHAVIOUR.md`.
* **Environment Detection:** Scans the project root to determine the correct testing and logging framework:
  * **JavaScript/Node:** `jest` / `Winston` (Detected by `package.json`)
  * **Ruby:** `rspec` / `Logger` (Detected by `Gemfile` or `Rakefile`)
  * **Java:** `mvn test` (JUnit) / `SLF4J with Logback` (Detected by `pom.xml` or `build.gradle`)
  * **C/C++:** `make test` (GoogleTest) / `spdlog` or `clog` (Detected by `CMakeLists.txt`)
  * **Python:** `pytest` / `logging` (Default fallback)
* **Execution Strategies:** Constructs the agent command based on the selected strategy:
  * **Strategy A (Auto-Heal - Default):** Implements the code first, writes necessary tests, and automatically fixes any test failures at the end.
  * **Strategy B (Strict TDD):** Enforces a strict Red-Green-Refactor loop immediately within the chat flow (writes a failing test, waits for failure, writes minimal code to pass, refactors).
* **Streaming Execution:** Spawns the agent (e.g., `aider`) using Python's `subprocess.run()` allowing the terminal output (git commits, test-fixing loops) to stream directly to the user in real-time.

**Command 4: `lupo archive [change_name]`** (Mapped from OpenSpec)
* Moves the completed Delta Spec directory from `openspec/changes/` into `openspec/changes/archive/` prefixed with the current date.

### Error Handling Requirements
* **Missing Files:** If `lupo execute` is run but no active Delta Spec exists, the CLI must cleanly abort and instruct the user to run `lupo propose` first.
* **Missing Dependencies:** If the external agent binary (e.g., `aider`) is missing from the system PATH during execution, the CLI must catch the `FileNotFoundError` and print explicit installation instructions for the missing tool rather than throwing a generic Python stack trace.

## 5. Evolution Engine & Self-Patch Protocol

Lupo Spec utilizes an automated dependency scanner (`sync_repos.py`) and a strict self-patching protocol to ensure the native Python framework stays synchronized with the upstream repositories it depends on. 

For comprehensive instructions on how to run the Evolution Engine and execute the Antigravity Self-Patch Protocol, please refer directly to the [Lupo Spec Evolution Guide](update.md) (`update.md`).
